# Final acceptance runner

`Invoke-NP-FinalAcceptance.ps1` is the canonical local acceptance orchestrator. It does not replace the existing harnesses: it selects them, checks prerequisites, captures their outputs and converts their results into one closed verdict.

## Profiles

| Profile | Selected scope |
|---|---|
| `Static` | Generated-reference drift and maintained static repository audits. |
| `Smoke` | `Static`, quick build/toolchain validation and a short functional run. |
| `Functional` | `Static`, full local tests, B/C runtime validation, P0 runtime coverage for all profiles/RBAC/diagnostics/alerts/observability/shutdown, controlled P3 and reset/recovery. |
| `Full` | `Functional`, multi-replica correctness, autoscaling experiments, fixture and live role Playwright journeys, accessibility, rate limiting, bounded HTTP Calibration+B0 and bounded full-system Calibration+B0. |

The exact stage lists and timeouts are versioned in `config/acceptance/final-acceptance.json`.

## Commands

Plan without executing:

```powershell
.\scripts\acceptance\Invoke-NP-FinalAcceptance.ps1 -Profile Full -PlanOnly
```

Run static checks:

```powershell
.\scripts\acceptance\Invoke-NP-FinalAcceptance.ps1 -Profile Static
```

Run a local smoke campaign:

```powershell
.\scripts\acceptance\Invoke-NP-FinalAcceptance.ps1 -Profile Smoke
```

Run the functional or full profile with controlled negative validation:

```powershell
$env:NP_RELIABILITY_AUTH_TOKEN = '<runtime token>'
# Optional override; otherwise the local .env POSTGRES_* values are used.
$env:NP_POSTGRES_CONNECTION_STRING = '<local PostgreSQL connection string>'
.\scripts\acceptance\Invoke-NP-FinalAcceptance.ps1 `
  -Profile Functional `
  -ExecuteControlledValidationP3 `
  -AcknowledgeNonProduction
```

The `Functional` and `Full` profiles also run the Phase 3 P0 stage. It starts from project-scoped clean local state and validates all 12 degradation profiles, real temporary RBAC identities, the exact 28-diagnostic catalogue, current B/C diagnostic prerequisites, alert transitions, RabbitMQ/InfluxDB/Grafana health, runtime evidence download and clean shutdown. Its detailed contract is documented in [P0 runtime functional coverage](p0-runtime-functional-coverage.md).

P3 remains fail-closed. Both switches, `NP_RELIABILITY_AUTH_TOKEN` and the `psql` client are required. PostgreSQL connectivity is taken from `NP_POSTGRES_CONNECTION_STRING`, an explicit parameter or the local `.env`, and the API must report an allowed non-production environment. The stage only passes after query pack 11 reconciles the exact generated `runLabel`: 10 executable cases must match, 2 fixture-dependent cases must remain blocked, retry paths must match and no unexpected accepted reading or risk assessment may exist.

## Verdicts and exit codes

| Status | Exit | Meaning |
|---|---:|---|
| `PASS` | 0 | Every selected stage executed and passed. |
| `FAIL` | 1 | At least one selected stage executed and violated its contract. |
| `BLOCKED_PREREQUISITE` | 2 | A required tool, token, service or explicit acknowledgement was absent. |
| `HARNESS_ERROR` | 3 | The orchestration process could not start or finish a stage safely. |
| `NOT_SELECTED` | 0 | Used only by `-PlanOnly`; no execution claim is made. |

A requested stage that did not run is never converted into a pass.

## Output contract

Every campaign records its Git commit, clean-tree state and a deterministic source fingerprint before stage execution. These fields allow the final delivery gate to reject evidence from a different snapshot.

Every campaign is written below:

```text
artifacts/final-acceptance/<run-id>/
```

The runner refuses output outside the repository `artifacts` directory. Existing non-empty output is also refused unless `-Overwrite` is supplied for that exact run directory.

The root contains:

```text
environment.json
run-spec.json
summary.json
SUMMARY.md
tests.csv
commands.csv
blockers.csv
evidence-manifest.csv
hashes.sha256
components/<stage>/
```

Each component keeps runner logs separate from the evidence generated by the delegated harness. Historical evidence is never promoted to current evidence. A delegated `acceptance-result.json` is treated as authoritative only when its status agrees with the process exit code; disagreement becomes `HARNESS_ERROR`.

## Build reuse

`-SkipBuild` is forwarded only to harnesses that explicitly support it. Use it only after a successful build in the same unchanged workspace. It does not cause the acceptance runner to assume that a historical build is valid.

## Standalone advanced matrices

The maintained matrices can still be run directly. Their default output is now local and run-scoped:

```powershell
.\scripts\testing\Invoke-SystemResetRecoveryMatrix.ps1 -SkipBuild
.\scripts\testing\Invoke-MultiReplicaTemporalMatrix.ps1 -SkipBuild
.\scripts\testing\Invoke-AutoscalingExperimentMatrix.ps1 -SkipBuild
```

All three refuse output outside `artifacts` and emit `acceptance-result.json` alongside their detailed evidence.


## Relationship to final delivery

A `Full / PASS` acceptance run is necessary but not sufficient for delivery. `scripts/release/Invoke-NP-FinalDelivery.ps1` strictly re-verifies the run, requires the same clean commit and source fingerprint, and then validates the packaged output. See [final-delivery-execution.md](final-delivery-execution.md).
